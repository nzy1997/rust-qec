# Issue 434 Repetition Release Speed Evidence Design

Issue: #434

## Context

Issue #433 is merged into `master` as PR #440 and provides
`benchmarks.rstim_vs_stim_simulator.run_speed_suite`, which builds the selected
`rstim` profile once and emits one `raw.jsonl`, `summary.json`, `report.md`,
and `environment.json` bundle for exactly the requested case labels.

Issue #434 asks to publish checked release-profile speed evidence for the
existing repetition-code sample case `rep-sample-d13-r13`. The evidence must
remain separate from `benchmarks/rstim_vs_stim_simulator/results/full/` and from
the existing d11/r100 selected-case release evidence under `results/release/`.
The checker must validate evidence completeness without claiming broad speed
superiority over Stim.

## Approaches Considered

1. Use the #433 suite runner for a one-case release bundle under
   `benchmarks/rstim_vs_stim_simulator/results/release-repetition-sample/`
   and add a general single-case release-speed checker. This is selected
   because it reuses the checked-output path, keeps evidence isolated, and
   gives reviewers the exact command requested by the issue.

2. Use the older single-case runner and copy its output into a new directory.
   This would also work for one case, but it bypasses the issue #433
   dependency and would not prove the suite runner can publish a narrow
   one-case bundle.

3. Extend the existing post-optimization d11/r100 checker to also validate the
   repetition case. This is rejected because the d11/r100 checker carries
   old/new artifact and site-manifest assumptions that are unrelated to this
   issue's narrower acceptance criteria.

## Design

The checked repetition-code evidence lives in:

```text
benchmarks/rstim_vs_stim_simulator/results/release-repetition-sample/
```

with exactly these published files:

- `summary.json`, generated by
  `python3 -m benchmarks.rstim_vs_stim_simulator.run_speed_suite --profile release --cases rep-sample-d13-r13 --warmup-rounds 0 --measure-rounds 1`;
- `report.md`, generated from that summary by the existing `rstim perf report`
  path;
- `environment.json`, generated by the suite runner and then marked with
  `evidence_kind = "repetition release speed evidence"`,
  `published_artifact = true`, and `source_issue = 434`.

The summary must contain exactly one case with `case_label =
"rep-sample-d13-r13"` and `workload = "sample"`. The three required variants
are `stim-cli`, `rstim-interpreted`, and `rstim-compiled`; each must appear in
the case's `variants` list with `status = "completed"`, and each must also
appear in `present_variants`. The checker does not enforce any speed ratio or
threshold.

## Checker

Add `tools/check_rstim_vs_stim_release_speed_case.py` with this interface:

```sh
python3 tools/check_rstim_vs_stim_release_speed_case.py \
  --results-dir benchmarks/rstim_vs_stim_simulator/results/release-repetition-sample \
  --case rep-sample-d13-r13 \
  --workload sample \
  --required-variants stim-cli,rstim-interpreted,rstim-compiled
```

On success it prints:

```text
PASS release speed case rep-sample-d13-r13
```

The checker validates:

- `summary.json`, `report.md`, and `environment.json` exist in `--results-dir`;
- `summary.json` is a JSON object with a `cases` list containing the requested
  case exactly once and no duplicate requested case entries;
- the selected case has the requested workload;
- every required variant is present in `present_variants`;
- every required variant has a `variants` entry with `status = "completed"`;
- `environment.json` records `profile = "release"`, profile/environment
  metadata fields (`rstim_binary_path`, `rustc_version`, `cargo_version`,
  `stim_cli_status`), and either `case_labels` containing the requested case or
  `case_label` equal to it;
- `report.md` mentions the selected case label.

Failures print one clear `ERROR release speed case check failed: ...` message
to stderr and exit nonzero. Missing required variants use the exact wording
`missing required variant <name>` for the negative control.

## Tests

Add `tools/test_check_rstim_vs_stim_release_speed_case.py` with subprocess
tests that build temporary result directories. The positive fixture covers a
valid one-case summary, report, and environment. Negative controls cover:

- missing `stim-cli` from `present_variants` and `variants`, expecting
  `missing required variant stim-cli`;
- duplicate requested case entries;
- wrong workload;
- required variant present but not completed;
- missing release profile/environment metadata;
- missing report file.

Run the issue-required checker command against the checked repetition evidence,
the checker unit tests, and `cargo test`.

## Scope Limits

Do not modify sampler internals. Do not alter existing artifacts under
`benchmarks/rstim_vs_stim_simulator/results/full/` or
`benchmarks/rstim_vs_stim_simulator/results/release/`. Do not publish broad
`rstim` versus Stim speed-superiority, parity, or all-workload claims from this
single repetition-code sample case.
