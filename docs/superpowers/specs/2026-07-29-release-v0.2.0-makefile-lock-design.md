# RustQEC v0.2.0 Makefile Release Design

## Goal

Publish GitHub release `v0.2.0` from the latest `master` using the repository's
`make release V=x.y.z` entry point. Keep the existing release scope: bump the
four versioned public crates (`rstim`, `rsinter`, `rbposd`, and `rmatching`),
create one release commit and annotated tag, push `master` and the tag, and let
the tag-triggered GitHub Actions workflow create the GitHub Release. This flow
does not publish crates to crates.io.

## Problem

The current target edits the four manifests and immediately runs
`cargo check --locked --workspace`. A clean-clone reproduction shows that Cargo
must first refresh the four workspace package versions recorded in
`Cargo.lock`; with `--locked`, it exits before checking the workspace. The target
also omits `Cargo.lock` from the release commit.

## Considered Approaches

1. Refresh the existing lock file offline, then verify with `--locked` and stage
   `Cargo.lock`. This is selected because it updates only repository-local
   metadata without resolving new network dependency versions, while retaining
   a final reproducibility check.
2. Remove `--locked` from the check. This is simpler but does not prove that the
   committed lock file is sufficient for subsequent locked builds.
3. Rewrite the relevant `Cargo.lock` entries mechanically. This is rejected as
   brittle duplication of Cargo's lock-file behavior.

## Selected Behavior

After updating the four manifests, the release target will:

1. run an offline Cargo command that refreshes the lock file using only locally
   available registry/cache data;
2. run `cargo check --locked --workspace` as the release gate;
3. stage the four manifests and `Cargo.lock` together;
4. preserve the existing commit, annotated-tag, push, and GitHub Release flow.

The target remains intentionally strict: a missing offline dependency, failed
workspace check, commit failure, tag collision, or push failure stops the
release.

## Verification

Before changing the target, a temporary clean clone must demonstrate the
current `--locked` failure after the four version edits. After the change, an
isolated dry-run fixture must demonstrate that the lock file is refreshed, the
locked workspace check succeeds, and `Cargo.lock` is included in the staged
release paths without creating a real commit, tag, or push.

Before publication, run the repository hygiene gate, toolchain checks, the full
Rust workspace tests, the Python tools tests, and the site build contract. Then
run `make release V=0.2.0` only from a clean, up-to-date `master`. After the push,
verify the tag, release commit, GitHub Release workflow, generated release page,
and unchanged clean worktree.

## Non-goals

- Publishing any crate to crates.io.
- Changing versions of `qec-code`, `qec-ilp-core`, `rilpqec`, or benchmark-only
  workspace packages.
- Changing the release-note generation workflow or compatibility policy.
