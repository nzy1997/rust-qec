# Issue 558 Generalized-Bicycle CSS Constructor Design

Date: 2026-07-27
Status: Approved by non-interactive Agent Desk standing policy
Scope: GitHub issue #558, Roadmap ID M2-02

## Summary

Issue #558 adds a parameterized cyclic generalized-bicycle CSS constructor to
`qec-code`. The selected design introduces a typed
`GeneralizedBicycleSpec { order, a_exponents, b_exponents }`, constructs the
standard two-block checks from cyclic circulants, and exposes the result through
the shared #553 `CssFamilySpec`/`construct_css` contract.

The constructor is pure Rust and deliberately bypasses the finite-group table
and lift layer. It uses the #554 sparse GF(2) primitives as the matrix boundary:
build circulants `A` and `B`, then produce `H_X = [A | B]` and
`H_Z = [B^T | A^T]`.

## Existing Context

- `.AGENTS/AGENTS.md` requires Rust 2024 style, focused integration tests, and
  exact verification commands before claiming completion.
- Issue #553 is closed and provides `RequestedFamilyId`,
  `CssFamilySpec`, `CssConstructionSpec`, `CssConstructionResult`, shared
  stats, provenance, JSON routing, and the existing `code css construct --spec`
  CLI path.
- Issue #554 is closed and provides `qec_code::sparse_gf2::SparseGf2Matrix`
  with checked canonical rows, transpose, and horizontal concatenation.
- The fixed `bb72`/`bb:*` parser in `codes/built_in_css.rs` is a legacy
  bivariate-bicycle utility and is not the requested `generalized_bicycle`
  family.

## Approaches Considered

### 1. Dedicated cyclic generalized-bicycle module - selected

Add `qec-code/src/codes/generalized_bicycle.rs` with the typed spec,
normalization, cyclic circulant construction, and sparse-check result. Extend
`CssFamilySpec`, `construct_css`, and `parse_css_construction_json` to route
`generalized_bicycle` through the module.

Benefits:

- uses the shared family contract exactly where new requested families belong
- keeps cyclic generalized bicycle separate from the older rectangular
  bivariate-bicycle built-in utility
- constructs matrices directly from cyclic circulants and sparse GF(2)
  primitives
- avoids any dependency on the finite-group table/lift layer
- gives deterministic metadata with normalized exponents and provenance

Costs:

- adds one more requested-family module and a small JSON parser helper

### 2. Reuse the legacy `bb` built-in parser

Represent cyclic generalized bicycle as `bb:lx=<order>,ly=1,...`.

Benefits:

- fewer new files initially

Costs:

- the metadata would be a legacy built-in construction, not requested-family
  `generalized_bicycle`
- the accepted parameter shape would not match the issue's typed
  `order`, `a_exponents`, and `b_exponents`
- the old bivariate route accepts two-dimensional shifts, which is broader than
  the cyclic exponent contract

This is not selected.

### 3. Route through finite-group lifts

Model the cyclic group and use the general group-algebra lift layer.

Benefits:

- reuses generalized algebraic machinery

Costs:

- violates the issue requirement that this constructor must not require the
  general finite-group table/lift layer
- adds unnecessary overhead for cyclic circulants

This is not selected.

## Public Contract

Add:

```rust
pub struct GeneralizedBicycleSpec {
    pub order: usize,
    pub a_exponents: Vec<usize>,
    pub b_exponents: Vec<usize>,
}
```

`CssFamilySpec::GeneralizedBicycle(GeneralizedBicycleSpec)` is a callable
requested-family variant and `CssFamilySpec::callable_requested_family_ids()`
includes `RequestedFamilyId::GeneralizedBicycle`.

Successful construction returns:

- `schema_version = 1`
- `construction_id = "generalized_bicycle"`
- `requested_family_id = Some(RequestedFamilyId::GeneralizedBicycle)`
- normalized parameters `order`, `a_exponents`, and `b_exponents`
- canonical sparse `H_X` and `H_Z`
- shared `n`, `m_x`, `m_z`, `rank_x`, `rank_z`, and `k` stats
- provenance adapter `generalized_bicycle`

For the issue fixture `order = 5`, `a = [0, 1]`, and `b = [0, 2]`, the result
also records `d_x = 3` and `d_z = 3`. Other generalized-bicycle instances leave
the optional directional distances unset until a general distance oracle is
added.

## Matrix Construction

For cyclic order `l`, row `i` of a circulant generated by exponents `S` has
support:

```text
{ (i + s) mod l : s in S }
```

The constructor builds:

```text
A = circ(a_exponents)
B = circ(b_exponents)
H_X = [A | B]
H_Z = [B^T | A^T]
```

Rows are returned in cyclic row order `0..order`. The sparse GF(2) matrix type
canonicalizes each row, so wrapped rows remain sorted and duplicate-free.

For `order = 5`, `a = [0, 1]`, `b = [0, 2]`, this produces exactly:

```text
H_X =
[[0,1,5,7], [1,2,6,8], [2,3,7,9], [3,4,5,8], [0,4,6,9]]
H_Z =
[[0,3,5,9], [1,4,5,6], [0,2,6,7], [1,3,7,8], [2,4,8,9]]
```

## Input Validation

The spec normalizes exponent lists by sorting them after validation. It rejects:

- `order = 0`
- empty `a_exponents`
- empty `b_exponents`
- any exponent `>= order`
- duplicate exponents after normalization

Accepting unsorted but otherwise valid exponent lists keeps the Rust and JSON
APIs convenient while still recording canonical normalized metadata.

## CLI And JSON Routing

Structured CLI requests use the existing shared route:

```json
{
  "schema_version": 1,
  "construction": "generalized_bicycle",
  "order": 5,
  "a_exponents": [0, 1],
  "b_exponents": [0, 2]
}
```

`code css construct --spec <path> hx` and `hz` parse the versioned JSON into
`CssFamilySpec::GeneralizedBicycle`, call `construct_css`, and serialize the
selected sparse rows through the existing matrix JSON format.

No compact legacy inline syntax is added in this issue. The parameter shape is
array-valued, and the structured constructor path is already the common contract
for that case.

## Testing

Add `qec-code/tests/generalized_bicycle.rs` with the issue-required exact tests:

- `generalized_bicycle_order5_matches_fixture`
- `generalized_bicycle_rejects_invalid_exponents`

The positive test verifies exact rows, canonical supports, orthogonality, stats,
fixture distances, Rust API construction, JSON lowering, deterministic metadata,
and CLI export through `code css construct --spec`.

The negative test verifies order zero, out-of-range exponents, duplicate
exponents, and empty `a`/`b` supports.

Required verification:

```text
cargo test -p qec-code --test generalized_bicycle generalized_bicycle_order5_matches_fixture -- --exact
cargo test -p qec-code --test generalized_bicycle generalized_bicycle_rejects_invalid_exponents -- --exact
cargo test
```
