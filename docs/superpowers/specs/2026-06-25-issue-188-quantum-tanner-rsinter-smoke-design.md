# Issue 188 Quantum Tanner Rsinter Smoke Design

## Context

Issue #188 verifies that quantum Tanner CSS checks generated by `qec-code` can be consumed by `rsinter` as ordinary CSS inputs. Issue #184 has already added the CLI export path:

```sh
cargo run -p qec-code -- code css quantum-tanner --spec qec-code/tests/fixtures/quantum_tanner/toric_d4.json hx
cargo run -p qec-code -- code css quantum-tanner --spec qec-code/tests/fixtures/quantum_tanner/toric_d4.json hz
```

`rsinter` already routes CSS benchmark inputs through `rsinter::bench::circuit_source::build_circuit_for_point`, which parses `sparse_rows` JSON and then calls `rstim::codegen::css::css_memory`. That path validates CSS width, sparse-row shape, and `Hx * Hz^T = 0` before the benchmark runner builds a DEM, samples shots, and decodes.

## Approaches Considered

1. Commit generated `toric_d4` `Hx` and `Hz` sparse-row fixtures under `rsinter/tests/fixtures/css` and run a tiny `rsinter` benchmark against them. This is the chosen approach because it proves the file-based consumer path without adding runtime dependence on the `qec-code` CLI or a quantum Tanner branch in `rsinter`.
2. Generate the sparse rows inside the test by invoking the `qec-code` CLI. This would prove the export command but would make the `rsinter` smoke test depend on another binary and would blur the boundary with #184.
3. Parse the quantum Tanner spec directly in `rsinter`. This is out of scope because #188 is about downstream CSS consumption, not adding a quantum Tanner importer.

## Chosen Design

Add two committed fixtures:

- `rsinter/tests/fixtures/css/quantum_tanner_toric_d4_hx.json`
- `rsinter/tests/fixtures/css/quantum_tanner_toric_d4_hz.json`

The fixture README will record that both files are generated from `qec-code/tests/fixtures/quantum_tanner/toric_d4.json` using the #184 CLI and that the known-answer chain comes from qLDPC `drafts/qLDPC/src/qldpc/codes/quantum_test.py`, `drafts/qLDPC/src/qldpc/codes/quantum.py`, and upstream `https://github.com/qLDPCOrg/qLDPC`.

Add one `rsinter` integration test named `quantum_tanner_toric_d4_css_fixture_smoke`. The positive control builds a minimal `BenchmarkSpec` with one Rust `rmatching` runner, `input_type = "css"`, the generated `Hx` and `Hz` fixture paths, one round, `p = 0.0`, and a tiny shot budget. It then calls `run_rust_benchmark`, reads the produced `results.jsonl`, and asserts that the run completed with ordinary CSS metadata and two logical observables.

The negative control creates a temporary non-orthogonal `Hz` sparse-row fixture derived from the positive fixture by changing one support entry. It runs the same benchmark path and asserts that the run is rejected with the existing CSS orthogonality error from `css_memory`. No special quantum Tanner code path is added.

## Validation

The required focused command is:

```sh
cargo test -p rsinter quantum_tanner_toric_d4_css_fixture_smoke -q
```

Before completion, also run:

```sh
cargo test -p rsinter -q
cargo test
```

## Out Of Scope

No threshold sweeps, new benchmark schema, qTanner/qLDPC importers, decoder changes, or circuit-level quantum Tanner scheduling are added.
