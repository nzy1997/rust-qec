# v0.3.1 staged candidate: verification incomplete

RustQEC v0.3.1 was staged as the first release candidate for promoting an
atom-loss envelope decoder out of Beta, but it did not complete the hardened
post-publication verification. Its GitHub Release is retained as a prerelease,
`rustqec-cli 0.3.1` was not published to crates.io, and `envelope-matching`
remains Beta for this version. v0.3.2 supersedes this candidate.
`envelope-mle` remains Beta, and conventional (non-Mid-SWAP) circuits remain
isolated checked examples. The v0.3.0 tag, GitHub Release, and native archives
are unchanged; v0.3.0 predates the envelope evidence bundle and has no verified
envelope promotion.

[`tools/release_version_policy.json`](../../tools/release_version_policy.json).

## The candidate Supported promise, precisely

After publication verification, `envelope-matching` is Supported for **flat loss-visible Mid-SWAP rotated
surface-code memory-Z circuits** within the circuit contract declared by the
executable matrix ([`docs/envelope-support.json`](../envelope-support.json))
and the measured operating envelope of the resource report
([`benchmarks/atom_loss/readiness/resources/`](../../benchmarks/atom_loss/readiness/resources/report.md)).
The finite tested size and loss points are witnesses of that domain, not an
untested Cartesian-product guarantee and not a universal latency promise;
larger configurations are unmeasured, not promised. The frozen CLI surface —
arguments, dataset interpretation, prediction packing, structured error codes,
statistics semantics, and the evolution/deprecation rules — is defined by
[`docs/envelope-compatibility-policy.md`](../envelope-compatibility-policy.md).

## How the promotion is verified

The per-decoder release-readiness gate (issue #716) must run against the exact
tagged source on Linux x86_64 and macOS arm64: the executable support matrix,
the independent correctness suite, the measured resource envelope, and one
installed-artifact contract report per official native target. A passing gate
promotes `envelope-matching` to Supported and keeps `envelope-mle` at Beta.

The intended durable proof, `envelope-support-evidence-v0.3.1.tar.gz`
(plus its `.sha256` sidecar), would have frozen the passing gate report, the consumed
matrix and policy, the support/correctness/resource evidence with retained
raw observations, and one archive-bound installed report per platform (issues
#719, #720). Download every release asset into one directory and run:

```sh
python3 tools/check_envelope_publication.py \
  --release-dir <download-dir> --expect-decoder envelope-matching
```

The hardened verifier reconciles the tag, source commit, both archive identities, the
per-platform installed reports, and the gate decision without rerunning the
evidence campaigns, prints the decoder scope and version, and ends with
`PASS envelope published support`. Release assets from a different revision
fail this verification. The retained v0.3.1 bundle predates the hardened input
binding and fails that check, so no valid
`envelope-support-verification-v0.3.1.json` marker exists. The marker would have
been the signal that allowed the website to render the Supported claim. The release-asset label
binds the marker digest, evidence-bundle digest, source commit and supported
decoder list; the website reconciles those values with GitHub's asset digests
rather than trusting the filename alone.

## Site and documentation

The website tutorial and concepts pages remain Beta for v0.3.1. They may only
upgrade for a later candidate when the matrix names that release and the
GitHub release API shows its evidence bundle, checksum, and digest-bound
post-publication verification marker; development, failed-publication, and
prerelease views stay Beta.
