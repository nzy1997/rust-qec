# v0.3.1 release: Envelope matching Supported

RustQEC v0.3.1 is the first release that promotes an atom-loss envelope
decoder out of Beta: `envelope-matching` is **Supported** within its verified
scope. `envelope-mle` remains Beta, and conventional (non-Mid-SWAP) circuits
remain isolated checked examples. The v0.3.0 tag, GitHub Release, and native
archives are unchanged; v0.3.0 predates the envelope evidence bundle and has
no verified envelope promotion.

## Package versions

| Package | Version | Notes |

| `qec-ilp-core`, `qec-code`, `rstim`, `rmatching`, `rbposd`, `rilpqec`, `rsinter` | 0.3.0 | Unchanged; not republished |

The repository tag records a tested snapshot of the 0.3 series: every public
crate shares the 0.3 major/minor line, none is ahead of the tag, and
`rustqec-cli` matches the tag version, per
[`tools/release_version_policy.json`](../tools/release_version_policy.json).

## The Supported promise, precisely

`envelope-matching` is Supported for **flat loss-visible Mid-SWAP rotated
surface-code memory-Z circuits** within the circuit contract declared by the
executable matrix ([`docs/envelope-support.json`](../envelope-support.json))
and the measured operating envelope of the resource report
([`benchmarks/atom_loss/readiness/resources/`](../../benchmarks/atom_loss/readiness/resources/report.md)).
The finite tested size and loss points are witnesses of that domain, not an
untested Cartesian-product guarantee and not a universal latency promise;
larger configurations are unmeasured, not promised. The frozen CLI surface —
arguments, dataset interpretation, prediction packing, structured error codes,
statistics semantics, and the evolution/deprecation rules — is defined by
[`docs/envelope-compatibility-policy.md`](../envelope-compatibility-policy.md).

## How the promotion is verified

The per-decoder release-readiness gate (issue #716) ran against the exact
tagged source on Linux x86_64 and macOS arm64: the executable support matrix,
the independent correctness suite, the measured resource envelope, and one
installed-artifact contract report per official native target. The gate
promoted `envelope-matching` to Supported and kept `envelope-mle` at Beta.

The durable proof travels with the release: `envelope-support-evidence-v0.3.1.tar.gz`
(plus its `.sha256` sidecar) freezes the passing gate report, the consumed
matrix and policy, the support/correctness/resource evidence with retained
raw observations, and one archive-bound installed report per platform (issues
#719, #720). Download every release asset into one directory and run:

```sh
python3 tools/check_envelope_publication.py \
  --release-dir <download-dir> --expect-decoder envelope-matching
```

The verifier reconciles the tag, source commit, both archive identities, the
per-platform installed reports, and the gate decision without rerunning the
evidence campaigns, prints the decoder scope and version, and ends with
`PASS envelope published support`. Release assets from a different revision
fail this verification.

## Site and documentation

The website tutorial and concepts pages render the decoder labels from the
version-bound matrix served at `/support/envelope-support.json`: the
`envelope-matching` badge upgrades to `Supported · v0.3.1` with a link to this
release only when the matrix's published support record is present and
complete; development or pre-release views keep the Beta label.
