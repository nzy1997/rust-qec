# rstim / Stim Parity Showcase Design

**Date:** 2026-03-14

## Goal

Produce a small, presentation-friendly experiment showing that `rstim` is already very close to `stim` on the main detector-error-model workflow.

The showcase should answer two separate questions:

1. Does `rstim gen` produce the same core circuits as `stim gen` on representative code families?
2. Given the same noisy input circuit, does `rstim analyze_errors` produce a detector error model that matches `stim analyze_errors`?

The output is meant for README text, a progress report, or a PR description. It is not intended to be a full benchmark suite or a claim of total Stim parity.

## Scope

The showcase uses three standard code families already supported by the repository:

- `repetition_code memory`
- `surface_code rotated_memory_x`
- `surface_code rotated_memory_z`

Each family is evaluated at two scales:

- `distance=5, rounds=5`
- `distance=13, rounds=13`

This yields six cases total. The matrix is small enough to run repeatedly, but large enough to show that agreement is not limited to toy inputs.

## Key Design Decision

`gen` comparison and `DEM` comparison must be treated as separate layers.

The repository currently exposes `rstim gen --after_clifford_depolarization` as a single convenience noise parameter routed through `NoiseParams::uniform(noise)`. In practice, that means `rstim gen` inserts more than just post-Clifford noise, while `stim gen --after_clifford_depolarization` only inserts post-Clifford depolarization.

Because of this semantic mismatch, a noisy `gen` diff would mix together two unrelated claims:

- whether the circuit structure is aligned
- whether the noise parameter interface is aligned

That would weaken the showcase. Therefore:

- `gen` parity is evaluated on noiseless circuits only
- `DEM` parity is evaluated on shared noisy circuits generated by `stim gen`

This isolates the main message: circuit structure is aligned in the noiseless case, and DEM generation is aligned when both tools analyze the same noisy circuit.

## Case Matrix

The exact showcase cases are:

1. `repetition_code memory`, `d=5`, `r=5`
2. `repetition_code memory`, `d=13`, `r=13`
3. `surface_code rotated_memory_x`, `d=5`, `r=5`
4. `surface_code rotated_memory_x`, `d=13`, `r=13`
5. `surface_code rotated_memory_z`, `d=5`, `r=5`
6. `surface_code rotated_memory_z`, `d=13`, `r=13`

For `gen` comparison, each case is generated without noise.

For `DEM` comparison, each case is generated from `stim gen` with a fixed nonzero noise setting. The simplest consistent choice is:

- `--after_clifford_depolarization 0.001`

Using one shared noise parameter keeps the experiment easy to explain and avoids turning the showcase into a generator-parameter study.

## Comparison Architecture

The experiment has two outputs:

1. A deterministic correctness harness.
2. A reporting harness that collects timings and formats a summary table.

The correctness harness is intended to be stable and suitable for local reruns or CI. It should fail fast and print the first meaningful mismatch.

The reporting harness is intended for presentation. It should gather timing data without turning runtime noise into a test failure.

Recommended implementation split:

- Integration test for correctness, under `rstim/tests/`
- Script or small helper command for timing and table generation, under `scripts/` or a dedicated example binary

This split keeps correctness claims reproducible while preventing machine load from causing flaky failures.

## Gen Parity Rules

`gen` parity is measured by running `stim gen` and `rstim gen` with the same `(code, task, distance, rounds)` and no noise flags.

Comparison should happen in two stages.

### Stage 1: Exact text check

Try a raw text equality check after stripping Stim's leading comment header. If the normalized texts are identical, record the case as an exact circuit match.

### Stage 2: Structural normalization check

If exact text does not match, parse both circuits and compare:

- instruction sequence after comment removal
- opcode histogram
- measurement count
- detector count
- observable count
- `QUBIT_COORDS` annotations
- `DETECTOR` annotations
- `OBSERVABLE_INCLUDE` instructions

This stage prevents harmless formatting or ordering differences from being misreported as meaningful parity failures.

For the showcase summary, `gen` status should be one of:

- `exact`
- `normalized`
- `mismatch`

## DEM Parity Rules

`DEM` parity is measured using a shared noisy circuit generated by `stim gen`.

For each case:

1. Generate a noisy circuit with `stim gen`.
2. Feed that same circuit text into `stim analyze_errors`.
3. Feed that same circuit text into `rstim analyze_errors`.
4. Compare the resulting detector error models semantically.

The semantic checks are:

- same number of `error(...)` instructions
- same error target sets
- same detector and `shift_detectors` annotations
- maximum relative probability error no larger than `1e-12`

This comparison deliberately focuses on semantics, not cosmetic text identity. The point is to show that the analyzed detector error model is effectively the same.

If a mismatch occurs, the harness should print the first failing target set or annotation difference instead of dumping a full unreadable diff.

## Timing Method

Timing is informative output, not a pass/fail gate.

For each command variant:

- run one warmup invocation
- run five measured invocations
- report the median wall-clock time

Commands to time:

- `stim gen`
- `rstim gen`
- `stim analyze_errors`
- `rstim analyze_errors`

The final table should include:

- case name
- `gen` parity status
- `DEM` parity status
- maximum DEM relative error
- `stim gen` median time
- `rstim gen` median time
- `stim analyze_errors` median time
- `rstim analyze_errors` median time
- `rstim/stim` ratio for both `gen` and `analyze_errors`

Timing thresholds should not be encoded as assertions. The table is there to support statements like "same result, same order of magnitude" or "same result, currently slower on larger cases".

## Failure Reporting

The correctness harness should fail with small, specific messages.

Preferred failure order:

1. command execution failed
2. circuit parse failed
3. `gen` structural mismatch
4. `DEM` target mismatch
5. `DEM` annotation mismatch
6. `DEM` probability mismatch beyond tolerance

Each failure should include the case label, such as `surface_code/rotated_memory_z d=13 r=13`, so the broken case is obvious without rerunning under a debugger.

## Out of Scope

This showcase does not attempt to prove:

- complete Stim feature parity
- parity for all generator tasks or all codes
- parity for noisy `gen` flag semantics
- exact textual identity of DEM output
- performance superiority

Those are larger follow-up tasks and should not be bundled into a single presentation experiment.

## Recommended Deliverables

1. A design-aligned correctness test covering the six cases.
2. A timing/report script that prints a markdown table.
3. A short summary paragraph for README, issue discussion, or PR text.

The summary paragraph should be written only after running the report script on the target machine, so the timing claims are backed by fresh numbers.

## Next Step

If implementation continues, start by building the correctness harness first. Once semantic comparison is stable, add the reporting script on top of the same case matrix and comparison helpers.
