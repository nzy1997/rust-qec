Benchmark methodology

Benchmark Methodology

Benchmark pages separate smoke checks, checked full artifacts, extended campaigns, and reference reproduction work so the site does not imply broader performance claims than the recorded evidence supports.

smoke

Local wiring checks with small cases. smoke checks verify wiring, command compatibility, and artifact shape; they are not statistical evidence.

full

Checked artifact campaigns with recorded provenance. full evidence can describe the committed checked run only within its recorded commands, hardware, versions, seeds, and budgets.

extended

Longer local or future campaigns that broaden case coverage but remain non-publishable until their artifacts and provenance are checked into the site manifest.

reference reproduction

Source-backed reproduction against an external paper, dataset, or repository commit. The reproduced scope and mismatches must be stated next to the result.

Required provenance

Every benchmark claim needs these fields

  • OS
  • CPU
  • Rust version
  • Python version
  • dependency versions
  • external repository commits
  • command line
  • seeds
  • build profile
  • shots or error budgets
  • date

Publishable Evidence

Publishable evidence is tracked by git, listed in the manifest, tied to source documents, and bounded by a manifest claims_limit. It may support statements about the specific committed artifact set, not broad decoder rankings.

Local-Only Evidence

Local-only evidence can validate commands and readiness, but ignored generated outputs and workstation-specific timings are not site-facing benchmark claims.

Claims Policy

Broad performance claims require full provenance, checked artifacts, source-backed interpretation, and an explicit manifest claims limit. Future benchmark families cannot appear without status and claims-limit fields.

Quantum circuit interchange

JSON Schema + protocol draft

QP101-ZY schema browser

A JSON format for ordered quantum circuits, repeat blocks, detector annotations, noise events, and visualization metadata used by rstim and qp101-viz.

Download JSON Schema Read Protocol Draft View Example

Core Model

QP101 documents keep execution order in an operations stream instead of flattening everything into gates. The schema covers gates, ticks, repeats, coordinates, detectors, observables, noise, and annotations.

Extensible By Design

Tool-specific data belongs in metadata, extensions, or operation-local annotations. The schema validates the stable structure while keeping room for downstream renderers and analysis tools.

Validation Boundary

The schema checks document shape. Whole-document semantic rules, such as comparing target indices with num_qubits, stay in the protocol draft.

Operation Types

Type Purpose Core Fields
gate Generic quantum gate or measurement operation. gate, targets, controls, raw_targets
repeat Nested block that preserves repeated circuit structure. count, body
tick Explicit timing separator. type
qubit_coords Coordinate declaration for one or more qubits. coords, targets
shift_coords Coordinate offset marker. delta
detector Detector annotation over measurement record sources. coords, sources
observable_include Logical observable include annotation. index, sources
noise Noise or fault operator preserving raw targets. gate, params, raw_targets
annotation Human-readable stream annotation. kind, text
